# Claude verification and concurrent work

- Umar's standing preference: Claude Opus 5.5 with high effort must review each substantive update or deliverable before it is presented as complete or applied to shared files. This follows his request that all updates be verified with that model. The request authorizes bounded review calls through the existing Claude subscription; it does not authorize purchasing credits, enabling API billing, switching providers or changing account settings.
- Request the exact model `claude-opus-5-5` and effort `high`, without automatic fallback. Record the command's requested effort and the returned model ID. Confirm that the result metadata identifies Opus 5.5. Do not claim that metadata independently proves the internal effort level when it does not.
- Send the exact proposed diff or artifact, task context and relevant test evidence. Resolve material findings and re-review changed substantive content before applying it. Preserve the verdict, reviewed content hashes and limitations. This review supplements tests and does not expand the task's authorization.
- Run the reviewer as a new tool-disabled or read-only session from an isolated scratch directory outside shared worktrees, with hooks/plugins disabled where supported. Never resume or alter an existing Claude session. Store review records in that scratch directory or a new task-specific folder under `~/.codex/reviews/`, outside shared project worktrees.
- Review receipts and mechanical HTML renderings of already-reviewed content do not require recursive re-review if they add no substantive claims. Verify that the rendering preserves the reviewed content. Status messages may report progress or blockers, but must not imply a review has passed before it has.
- If the exact model is unavailable, authentication fails, the returned model cannot be confirmed, or material findings remain unresolved, mark the work pending verification. Continue independent read-only work; do not apply the pending shared edit or present it as verified. Report the limitation without silently substituting a model. Stop a review loop when the same unresolved issue recurs without new evidence; report it rather than repeating calls indefinitely.
- Before editing shared project files, inspect worktrees, branch heads, uncommitted files and available coordination evidence for Claude's active work. Record the intended file scope in the task plan or status shown to Umar. Use an isolated worktree or scratch directory for overlapping work and keep changes unapplied until overlap is resolved.
- Do not overwrite, revert, stash, stage or delete Claude's changes, and do not stop its sessions, servers or processes. Recheck target-file hashes immediately before applying reviewed edits; if a target changed, abort the write, reconcile with its current contents and re-review the changed result. Resolve unclear ownership before editing a needed shared file.
- Process working directories and clean git status do not prove another agent is idle or identify every file it may edit. State the checks and isolation actually used; do not promise conflicts are impossible. Leave earlier artifacts in active worktrees alone and identify their reviewed commit when newer work has advanced beyond them.
